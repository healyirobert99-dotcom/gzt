### 为什么必须做成归档而不是 DELETE

五张子表（`research` / `trade_plans` / `execution_reviews` / `decision_ledger` / `trades`）
**全部 `ON DELETE RESTRICT` 引用 `securities(id)`**，且应用开着 `PRAGMA foreign_keys=ON`；
`decision_ledger` 是 append-only、必须保留"当时的判断"。实测 17 只标的**全部有历史**，
没有一只是"干净"的 → 任何 DELETE 都会永久抹掉历史。

## 设计

- `securities.archived_at TEXT` 是**可见性开关**，与交易状态 `status`（5 项白名单）**正交**，
  不是"第六种状态"。
- 归档 / 恢复各追加 1 条 `decision_ledger`（`event_type='标的归档'` / `'标的恢复'`），
  与「状态变更 / 研究更新 / 备注」的既有留痕约定一致。
- `list_securities(mode)` 三模式：`active`（默认，`archived_at IS NULL`）/ `only` / `all`，
  三模式自洽（active ∪ only == all，互不相交）。
- `GET /api/securities?archived=` 走**白名单** `_ARCHIVED_MODES`，非法值（`bogus`/`2`/`maybe`）
  一律 **400**，不静默兜底。

## 本轮新发现的环境陷阱（已写入 `ENV-TRAPS.md`）

agent-browser 五条会**伪装成产品 bug** 的坑：
1. **带空格的复合选择器被截断成第一个 token** —— `click ".mfoot button.primary"` 实际点的是
   外层 `.mfoot` div，却照样报 `✓ Done`。→ 一律用无空格 `>` 子选择器。
2. **`click` 不自动滚动进视口** —— 视口外的元素点击静默落空（首页「已归档」区在绝对
   y≈3381）。→ 先 `set viewport 1280 4000`。
3. **会话跑久了 `:hover` 失效** —— `get styles` 恒读默认态，悬停断言假红；而同一批次的
   `click` 仍成功（Playwright 给元素自己补 hover）。→ `agent-browser close --all` 重开。
4. **`✓ Done` 只代表命令已派发，不代表点中了元素**。
5. `get text` **取不到折叠 `<details>` 里的内容** → 先展开再读。

Python 驱动 agent-browser 的两条：
6. `agent-browser` 是 sh 垫片，`subprocess` 直接调它 → `FileNotFoundError [WinError 2]`。
   须直调 `<node.exe> node_modules/agent-browser/bin/agent-browser.js`。
7. **`subprocess.run(capture_output=True, timeout=)` 会永久挂死**：超时只 kill node.exe，
   派生进程仍持有 stdout 管道 → `communicate()` 等不到 EOF，实测无声挂了 **20 分钟**。
   → 输出重定向到文件（不接管道）+ `Popen` + 超时 `taskkill /F /T`。

### 新踩的环境陷阱（已补进 `ENV-TRAPS.md` ⑪）

**一次 batch 里多条命令的输出会被合并进同一个块，`✓ Done` 并非每命令一枚。**
探针 `probe_count.py` 实测：3 个 `get count` + 1 个 `get text` 的输出挤成一块
`'\n\n17\n\n0\n\n06:10\n\n17\n'`。于是 `browser_e2e_archive.py` 里 `ints()` / `last_int()`
（假设"每命令一块、块内容恰好是数字"）**只在 count 恰好在批次末尾时才侥幸正确**。

首轮边界脚本因此 **4 条假红**（`card=17` / `btn=None` / `drawer=None` / `card=None`），
而**同一批次的文本证据全 PASS** —— 极具迷惑性，差点误判成"归档到 0 张卡页面就坏了"。

**正解**：`get count` **独占一个批次**（不与 `get text` 混，否则文本里的纯整数行会污染读数），
再**按行**收纯整数行（`0` 也会照常输出，能区分"一个都没有"与"读数失败"）。
已提为公共 helper `browser_e2e_archive.py::count_values()`，两份脚本共用。
修正后：边界 **28/28**、E2E 回归 **38/38**（**未改动任何既有断言**）。

## 边界检查发现的**真缺陷**：归档 × A/H 关联（已修）

把边界检查再往外推一层 —— 查「归档会不会牵连别的字段」—— **揪出一条真缺陷**，
且正是归档功能自己引入的回归。

### 症状

A 关联 B（`securities.ah_link_id`）。把 **B 归档**后，打开 A 的「编辑基本信息」，
**只改行业/备注再点保存**，A→B 的关联就被**静默清空**（`ah_link_id` 写成 NULL），
提示仍是「基本信息已更新」—— 用户完全无从察觉。

### 根因

`openBasicModal` 里 A/H 下拉的候选项来自 `S.secs.filter(...)`，而 **`S.secs` 不含已归档标的**
→ 下拉里没有 B → 浏览器回落到首项「— 无 —」→ 提交 `ah_link_id=""` →
后端 `ah in (None,'') → None` 写回 NULL。
后端本身**不校验归档状态**（允许关联已归档标的），所以问题纯在前端的候选集构造。

### 修法（最小改动，两处同一口径）

- `openBasicModal`：候选里**补回被归档的关联项**并标注「· 已归档」；**仅在"当前已关联
  且该关联不在活跃列表"时补**（不无条件把已归档标的塞进下拉）。
- `rowHtml`（标的库）：A/H 关联显示同样回退到 `S.archived`，并附「（已归档）」，
  否则关联说明会凭空消失。
