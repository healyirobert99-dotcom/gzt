## 追加：第八面 · 「×」的几何（右上角到底有没有被挤）

用户的原话是"**在右上角出现一个叉**"。此前所有验证只断言过 `opacity` / `pointer-events`
（"悬停才显形"），**从没量过它到底在哪、有没有压住别的东西**。
CSS 里 `.terminal-card-head { padding-right: 24px; }` 看着就是为 × 预留的槽位
—— 但那是**推导**。补了一次实测。

### 探针：`probe_geometry_archive_btn.py`（26 断言，4 个视口）

1440 / 1000 / 768 / 560px，每个视口量 17 张卡片的 `getBoundingClientRect()`：

| 断言 | 结果 |
|---|---|
| ① × 完整落在卡片内（不被 `overflow:hidden` 裁） | 17/17 × 4 视口 |
| ② × 距右边缘恒为 10px（= 9px CSS + 1px border） | 4 视口全同 |
| ②b × 距上边缘恒为 10px | 4 视口全同 |
| ③ **× 与状态徽章不重叠** | 17/17 有徽章，最小间隙 **9.0px** |
| ④ × 热区恒 20×20px | 4 视口全同 |
| ⑥ × 与徽章间隙**跨视口恒定**（卡片宽 419→253px 仍 9.0px） | PASS |
| ⑦ 卡片宽度确实随视口变化（4 种） | 证明 ⑥ 不是"布局没动"的假绿 |

**结论：无缺陷。** × 在 560px 窄视口下也不压徽章、不越界、不变形。

### 首跑 8 条 FAIL —— 又是**探针自己**（第三次）

②/②b 系统性报 `10.0` vs 期望 `9.0`。根因：`getBoundingClientRect()` 量的是 **border-box**，
而 `position:absolute` 的 `top/right` 相对的是**包含块的 padding box**；卡片有
`border: 1px solid`，故实测偏移 = CSS 值 + border-width。
**修法不是把期望改成 10.0**（那就变成魔数），而是把 border-width 从 DOM 读出来推导。
→ 记 ENV-TRAPS ⑲。

### 新增离线契约 `§D#15` / `§D#15b`（133 → **135 断言**）

把这条**布局耦合**固化下来——`position:absolute` **不参与文档流**，邻居不会被自动挤开，
完全依赖人工预留：
```
× 的占位 = right + width           = 9 + 20 = 29
头部预留 = card.padding-right + head.padding-right = 14 + 24 = 38
不变式：预留 > 占位（差值 9px 即实测间隙）
```
解析要点（两个坑）：
- 取"**最后一条**声明了 `padding` 的 `.terminal-card`"（模拟 CSS 级联，后写的生效）；
- 简写 `padding: 12px 14px 10px` 的右值取**第 2 个**分量（3 值 = 上·左右·下）；
- **不能加 `^` 锚点** —— 多条 `.terminal-card` 规则是**单行**写的，`padding:` 不在行首
  （首跑因此解析出 `card_pr=None`）。

负向验证 M13/M14（新增两次注入，共 **14 次注入 / 28 断言**）：
- M13 把 head 的 `padding-right` 清零 → §D#15 红；
- M14 把 × 放大到 40px 却不改预留 → §D#15 红。
